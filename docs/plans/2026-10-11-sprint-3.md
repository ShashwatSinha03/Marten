# Sprint 3 — Release hardening implementation plan

**Goal:** Prepare the fixture-only beta for configuration and measured hosted acceptance.

**Architecture:** Preserve single-instance API, private Supabase storage, browser-only frontend and user-provided Gemini key. Add bounded physical-retention cleanup and network failure UX without expanding target execution scope.

## Specialist tasks

1. Backend/security: query oldest expired records directly, independent of history pagination. Delete storage before metadata; retain failed cleanup records for retry. Run startup and periodic single-flight cleanup while awake and drain on shutdown. Add meaningful retry/lifecycle/transport tests.
2. Deployment: preserve cleanup metadata after auth account deletion with nullable owner FK SET NULL, expiry index and migration instructions. Add credential-free CI and a concrete deployment/live acceptance checklist for Vercel, Render and Supabase. No cloud mutation.
3. Frontend/UX: bounded fetch/body timeouts, slow-service explanations, manual reconnect and screenshot retry, visible history/auth failures, exact expiry. Never automatically replay mutation requests.
4. Orchestrator: inspect specialist diffs, run full tests/typechecks/build, perform bounded UI verification, and record results and remaining live gates.

## Acceptance

Expired rows are inaccessible immediately and physically cleaned in retryable bounded passes when the API is awake. No user key is logged or persisted. Failed network requests preserve existing evidence and explain uncertain mutation outcomes. CI executes real controlled Chromium tests. Public URL execution stays disabled pending deployment isolation certification.

Live Supabase/OAuth/Gemini verification, Render memory/sandbox/egress checks and actual deployment require dedicated user resources and remain a separate acceptance stage; local checks do not certify them.
